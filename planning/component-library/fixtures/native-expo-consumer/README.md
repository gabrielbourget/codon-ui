# External Expo consumer verification fixture

This non-shipping fixture prepares verification of the React Native CLI bridge without changing the CLI, registry schema, native dependency graph, workspace dependencies or web behavior. It uses only Node built-ins. It does not require the unpushed Mac work to exist in this checkout. Native source selection and dependency packaging belong to the separate implementation task.

Admission reference: `NATIVE-CELL-03` and roadmap Sections 3.3.9–3.3.12 were read for this preparation. The selected scope is source-distribution lifecycle and consumer integration preparation (historical G06), with no component-cell qualification, native attempt or ledger promotion. An actual native run retains the maintained admission, platform, deadline and cleanup requirements.

## Run the fixture tests

From the Codon UI repository root:

```sh
node --test planning/component-library/fixtures/native-expo-consumer/consumer-probe.test.mjs
```

These tests exercise real temporary files, dependency trees, symlinks/hardlinks and child-process exit/timeout behavior. The lifecycle commands inside the tests are explicitly synthetic writers. A passing fixture test means the checker distinguishes those positive and negative controls; it does not mean the RN CLI, codegen, autolink, native build or device passed.

## Seed a clean consumer

```sh
repo="$PWD"
fixture="$repo/planning/component-library/fixtures/native-expo-consumer"
consumer="$(mktemp -d /tmp/codon-external-expo-XXXXXX)"
evidence="$(mktemp -d /tmp/codon-external-evidence-XXXXXX)"
node "$fixture/consumer-probe.mjs" seed "$consumer" "$repo" > "$evidence/seed.json"
```

The seed reads exact Expo/React/RN/Babel/TypeScript pins and the package-manager version from the current repository; it neither installs packages nor changes the repository's manifests/lockfile. Its initial runtime dependencies are Expo, the development client, React and React Native. Its development-only React DOM peer uses the existing showcase pin matching React, preventing pnpm from auto-selecting an incompatible optional web peer; it does not select a DOM implementation for native components. The repository release-age policy is copied to a consumer `.npmrc`, without creating a containing workspace. The implementation's selected dependency graph must supply its own required runtime dependencies once. Preserve the repository's release-age policy when preparing the separate consumer install; the seed does not bypass it or install packages. Record the eventual consumer lockfile and use frozen reinstalls for reproducibility.

The consumer must be outside the repository and any ancestor pnpm workspace. No workspace links, `NODE_PATH`, Metro `watchFolders`/`extraNodeModules`, Babel aliases back to the repo, whole-library import or symlinked component source should rescue a missing distribution file. The default Metro config comes from Expo without custom resolution. `SelectedComponents.tsx` deliberately throws until it imports the actual CLI-installed component sources and composes their actual required providers. This prevents a core-RN-only screen from masquerading as component integration. Build/type/export success alone still does not prove that the selected components mounted.

For the real shared smoke, replace that one app-owned module with the installed Input and an overlay-triggering component, plus a second component that shares the first component's native/shared dependency. Use the implementation's actual import paths, API and providers. Include one controlled draft readout and counter, open/dismiss readout and a bounded scrolling region. Keep the app's required Intl initialization explicit before component imports where the selected graph needs it. Do not copy the showcase or import the full native barrel as a workaround. Keep the original throw stub's seed hash in the evidence and record the final smoke source separately.

## Bind the real CLI without guessing its interface

Copy `lifecycle.example.json` into the evidence directory. Replace every `REPLACE` path, version, codegen name and digest with the implementation's actual selected outputs. Hash expected bytes independently from the frozen registry producer rather than from the newly installed consumer file. The example paths are placeholders, not a proposed registry or native-package layout. Use an explicit local adapter with argv dispatch for the real CLI's init/add/preview/update/status commands; each command inherits the external consumer as cwd. The adapter must await the real command, forward its output/exit status and never substitute a synthetic writer. No production CLI flags are invented here.

Prepare a fixed v1/v2/v3 local registry producer: v1 installs two selected components sharing a helper and native dependency; v2 changes the first component while keeping shared/native requirements stable; v3 changes the same file after the consumer edit. This exercises a real upstream update rather than an unchanged-registry no-op. Give the adapter only those immutable producer paths; it should not edit the repository or replace source in place. Add a separate native/spec-changing producer when checking rebuild invalidation.

```sh
node "$fixture/run-lifecycle.mjs" \
  "$consumer" "$repo" "$evidence/lifecycle.json" "$evidence/lifecycle"
```

The runner executes argv directly with no shell and a default two-minute timeout per CLI command. It requires a fresh evidence directory, stops at the first failure and retains logs, before/after hash inventories and `report.json`; the CLI entry point exits nonzero on failure. Use it only for finite CLI operations that await their children, not SDK builds, background servers or device orchestration. Native runs need their existing lifecycle owner. `nativeBuildVerified` remains false even if all source-lifecycle checks pass.

`expect.unchanged` compares file names and SHA256 values, including source, config and lockfiles. Inventories intentionally omit `.git`, `node_modules`, `.expo`, `.gradle`, `build`, `dist` and `Pods` directories; they do not prove absence of package-manager execution or generated-cache mutation. Use the real CLI report and installed dependency checks for that separate assertion. `expect.preserved` names exact regular files. `expect.files` requires byte-exact editable copies and rejects symlinks/hardlinks. These assertions do not certify semantic lockfile ownership/provenance; retain existing CLI contract tests and add RN-specific report assertions in the CLI owner's test suite.

`expect.dependencies` is a map of exact expected fixture pins. `expect.contexts` must include `.` and every relevant physical selected native package root. Package checks perform fresh ordinary `node_modules` ancestor lookup from each context, read the installed manifest and compare real paths; they do not use Node's cached resolution result. This detects an extra same-version React copy as well as version drift and resolution outside the consumer. This is targeted context coverage, not an exhaustive package-manager graph audit or Metro-resolution proof. For pnpm, use a package's resolved physical root under the external consumer's `.pnpm` directory when selecting fingerprint roots, rather than snapshotting a symlink in `node_modules`.

For native inputs, capture the whole selected native source package, codegen/spec and JS wrapper directories, autolink/build/podspec files, package manifests, consumer lock and Codon provenance lock. Directory captures detect added and deleted files as well as changed bytes. Capture roots must include the complete selected native dependency closure supplied by the implementation owner. The fixture does not decide that closure. Files under the ignored generated directories remain excluded. `assertNativePackage` checks source/package shape only; neither a present podspec nor a present spec is compiler/autolink acceptance.

`expect.autolink` reads the actual command's JSON stdout. It checks the scanned consumer root, required selected package roots/names/versions, forbidden unselected package names, exact platform paths and values such as descriptor lists, native library name and Java package registration. Bind these expectations to the separate graph owner's approved output. `expect.codegen` reads the generated schema file and requires exactly the selected module names and valid Component/NativeModule types. The example includes both OS scanner commands and a local adapter step for the pinned schema parser. Neither check proves generated SDK artifacts compile or providers register at runtime. Run Expo's own duplicate verifier as well: a JSON object cannot represent duplicate identical dependency keys.
