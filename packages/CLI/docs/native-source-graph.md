# Native source graph foundation

The read-only `buildNativeSourceGraph` helper in `src/helpers/nativeSource/graph.ts` prepares source/dependency evidence for later React Native registry integration. It is internal to the CLI source and is not connected to CLI commands, project detection, registry manifests, install plans, lockfiles or file writers. Existing add/update/diff/remove behavior is unchanged.

Pass the canonical `packages/react-native` directory as `sourceRoot` and an explicit map of component names to package-relative TypeScript entrypoints:

```ts
const graph = await buildNativeSourceGraph({
  sourceRoot: "/checkout/packages/react-native",
  entrypoints: {
    button: ["src/components/Button/Button.tsx"],
    time: ["src/components/TimePicker/TimePicker.tsx"],
  },
})
```

Files have package-relative paths, SHA-256 hashes of their original bytes and the sorted component owners that require them. Source/type edges retain imports, reexports, literal dynamic imports, `require`, import types and import-equals references. Native edges record registration, build membership, quoted includes and owned Java type dependencies. Ancestor license/notice/upstream files accompany selected source. Dependencies preserve the full imported subpath, declared package/range, runtime/peer classification and importing files, including private React Native subpaths that a later consumer verifier must assess. Cycles terminate and shared paths appear once. A fresh call after an edit produces a changed hash; it neither overwrites nor authorizes overwriting local edits.

The maintained native adapter currently has a single coupled build boundary: one codegen directory, the iOS pod's source globs, Java package registration, shared JNI/motion library and Fabric overlay target. Any runtime-reachable spec attaches that complete adapter once, with its requiring component owners. All ten specs accompany it even when a selection reaches fewer specs at runtime. A type-only spec reference retains source declarations without activating the adapter. Per-component native pruning needs a separate source/build refactor; this graph does not claim that current native translation units can be installed independently.

Native validation reads source as data and checks all discovered specs against iOS module/component providers, actual implementation classes (including multiple providers in `CUIFormMetadata.mm`), Android manager/module factories and module metadata, generated manager delegates and the custom owned focus descriptor. It checks the pod's source/public-header declarations, Gradle codegen/prefab wiring, both CMake targets, every owned C++ translation unit against the explicit motion source list, generated overlay source globs, the provider forwarding header/function and quoted owned includes. Native inventory includes Android manifest/consumer rules, Swift, C++ headers, licenses and upstream provenance; build/test outputs are excluded. Registration comments do not satisfy checks, and native config is parsed as a static object rather than imported or executed.

The prefab package `codon-ui_react-native` and link `codon-ui_react-native::codon_motion` are hardcoded by the current overlay build. Renaming a copied native package without coherently rewriting and verifying those references produces findings. The current package/codegen/Java/pod/target identities are deliberately a supported source profile, not configurable install destinations.

`valid` means the selected source graph and supported registration checks have no findings. It does not establish generated code correctness, native compilation/linkage, Metro resolution, autolinking, an installable registry item or installed-device behavior. The static native checks do not interpret arbitrary Ruby, Groovy or CMake. Dynamic native config and nonliteral JS imports are findings; unsupported platform variants, missing imports, undeclared packages, test imports, package escapes and symlinks also prevent validation. Invalid root/package manifests reject the call. The reader assumes a quiescent checkout; it is not a snapshot transaction against concurrent filesystem changes.

Later integration must choose component entrypoints, map source paths into editable consumer ownership, adapt the native package/build identities, preserve all codegen/provider/descriptors and shared sources, incorporate hashes/owners into the existing lock and update/diff/remove safety, and run actual generated-code/Metro/native consumer checks. The graph provides source evidence for that work and performs no writes or dependency installation. Mac project detection/routing work remains a separate integration boundary.

Run `pnpm -F @codon-ui/cli test:native-source`. These focused tests also run at the end of the existing CLI test command. They cover the maintained public barrel, selected component closures, shared ownership/hashes/notices, cycles, type-only specs, escaping/symlink paths, unresolved/platform/test imports, and mutated provider/package/descriptor/CMake/Gradle/prefab registrations. No SDK, emulator, simulator or publication step is invoked.

## Table ownership and extraction design

`inspectTableNativeOwnership(reader, adapter, includeTable)` in `ownership.ts` is a read-only extraction plan for current native bytes. It partitions every inventoried input exactly once, records cross-unit dependencies and hashes the embedded Table boundaries. Keeping the complete source returns `source-complete`; omitting Table returns `blocked` with retained-source references and build-membership findings. `selectiveInstallValidated` is always false. No native implementation has been extracted or selectively installed by this pass.

The Table-owned files are `cpp/table/StickyConstraints.h`, `StickyPresentation.h/.cpp`, `StickyStyle.h/.cpp`, `ios/CUITableStickyPresentation.h/.mm`, and `android/src/main/java/com/codonui/input/CUITableStickyPresentation.java`: eight files total. These form an ownership boundary, not a removable file list. Table reuses shared `PositionOwnership`, `FabricSnapshot`, `NativeStyle` and `PopStyle` helpers. The shared iOS `CUIMotionSnapshot.mm` retains the synchronous calling-runtime method map, combined pop/Table session and driver cleanup; Android `CUIMotionSnapshotModule.java` retains Table handles, callbacks, failures and invalidation; `MotionSnapshotJNI.cpp` retains Table native functions and registration inside its sole `JNI_OnLoad`. Those three shared implementations point back into the Table files. The source dependencies therefore currently run in both directions.

The spec's `tableStickyPresentation` method is marked `shared-abi`, separately from the three `feature-implementation` boundaries. The stable signature alone need not prevent extraction: an optional implementation can remain behind the existing shared ABI. The current generator places that method inside `CUIMotionSnapshot` on both platforms. There is no independent Table codegen binding, iOS provider, Android package or descriptor. The ownership plan assigns all existing registration identities to shared code and rejects repeated identities even when the same unit claims them twice. New Table-named files or changed embedded signatures/lifecycle markers stop the supported profile for review.

The proposed production refactor keeps one package, pod, `CodonNativeInputSpec` namespace, `CodonInputPackage`, existing module/component provider set, `codon_motion` prefab/library and `JNI_OnLoad`. It preserves the current public component API and the shared `CUIMotionSnapshot` ABI. It does not introduce a second Table copy of any of those registrations.

1. Define a private shared feature interface for the synchronous Table request and retirement boundary. Preserve the actual calling JSI runtime/Fabric manager on iOS, serialized admission, native mount callbacks, lease/owner/window checks, latched failures and cleanup ordering. A generated absent-feature factory returns unavailable without referencing a Table implementation; the existing method can report that the feature was not installed. This is a future implementation contract, not a new current runtime behavior.
2. Move the Table session/driver lifecycle out of the shared pop session and Android motion module into Table-owned implementation files. Make the Java driver depend on its feature owner/interface rather than `CUIMotionSnapshotModule`. Keep the reused Fabric/style/position infrastructure in shared code. The shared-only source must contain no direct include, Java type or symbol reference to an excluded Table implementation.
3. Move Table JNI functions into a Table-owned translation unit and compose its registration callback into the existing loader only when selected. Keep exactly one loader and register each native method exactly once. Shared-only Java/JNI code must have no residual Table native-method acquisition or cleanup call. This requires matching Android/iOS compiler and lifetime checks; text substitutions cannot establish that contract.
4. Materialize one native package from shared files plus selected feature files, with a generated feature factory/registration aggregate and exact CMake/pod source membership. Keep the current prefab identity unless a separately validated identity rewrite is implemented. Retain one merged spec directory/codegen invocation and the existing provider/descriptors once; do not register the entire shared package again for Table. Source ownership, hashes and update/remove decisions must later feed the existing editable-source lock lifecycle.
5. Validate shared-only and shared-plus-Table selections from their actual generated configuration: schemas and module methods, provider maps, generated sources and target ownership, pod source/input lists, Java factory/feature references and every owned include. Require real Gradle/CMake and CocoaPods/Xcode compilation/linkage for both selections, followed by the affected runtime/lifecycle checks. Do not promote component acceptance cells or claim selective installation from a source plan or successful code generation.

There is an additional build constraint: React Native generates a default `react_codegen_CodonNativeInputSpec` OBJECT target. The maintained custom `react_codegen_CodonNativeOverlay` target already owns the generated root `*.cpp` and `react/renderer/components/CodonNativeInputSpec/*.cpp` sources and forwards the generated module provider. Enabling both source-owning targets compiles the same generated translation units twice. `validateNativeCompileOwnership` detects that collision from expanded source identities. A future feature selector must preserve the current custom-overlay route or explicitly redesign ownership; adding the default codegen target alongside it is invalid.

The focused ownership tests invoke the pinned React Native schema/native-code emitters for Android and iOS, the real iOS module/component provider emitters, and the real `ReactCodegen.podspec` emitter into temporary directories. They verify all ten schema bindings, the existing three module/seven component providers, the shared Table method, actual generated CMake source ownership and duplicate-target rejection. A repeated-library probe demonstrates duplicated component entries in real provider output and checks that the ownership guard rejects duplicate claims. The podspec-emitter test uses copied real specs and a synthetic `.xcodeproj` directory only to supply path metadata; it is not an Xcode consumer or a pod installation. Native CMake configuration, CocoaPods execution, SDK compilation/linkage and selective runtime behavior remain unverified here; this cloud image has no CMake/Ruby/Xcode toolchain, and no toolchain installation is part of this pass.
