# Native source graph foundation

The read-only `buildNativeSourceGraph` helper in `src/helpers/nativeSource/graph.ts` prepares source/dependency evidence for later React Native registry integration. It is internal to the CLI source and is not connected to CLI commands, project detection, registry manifests, install plans, lockfiles or file writers. Existing add/update/diff/remove behavior is unchanged.

Pass the canonical `packages/react-native` directory as `sourceRoot` and an explicit map of component names to package-relative TypeScript entrypoints:

```ts
const graph = await buildNativeSourceGraph({
  sourceRoot: "/checkout/packages/react-native",
  entrypoints: {
    button: ["src/components/Button/Button.tsx"],
    time: ["src/components/TimePicker/TimePicker.tsx"],
  },
})
```

Files have package-relative paths, SHA-256 hashes of their original bytes and the sorted component owners that require them. Source/type edges retain imports, reexports, literal dynamic imports, `require`, import types and import-equals references. Native edges record registration, build membership, quoted includes and owned Java type dependencies. Ancestor license/notice/upstream files accompany selected source. Dependencies preserve the full imported subpath, declared package/range, runtime/peer classification and importing files, including private React Native subpaths that a later consumer verifier must assess. Cycles terminate and shared paths appear once. A fresh call after an edit produces a changed hash; it neither overwrites nor authorizes overwriting local edits.

`nativeRuntimeOwners` records static value-import reachability per spec, separately from the owners of the complete native build unit. Type-only edges and specs copied solely for codegen do not create runtime-owner claims. This is source evidence, not an observed native call trace or permission to prune a spec. Parsed imports and import resolutions are reused within one graph call; caches do not persist across calls, and fresh calls still observe edited source. The same quiescent-checkout assumption applies.

The maintained native adapter currently has a single coupled build boundary: one codegen directory, the iOS pod's source globs, Java package registration, shared JNI/motion library and Fabric overlay target. Any runtime-reachable spec attaches that complete adapter once, with its requiring component owners. All ten specs accompany it even when a selection reaches fewer specs at runtime. A type-only spec reference retains source declarations without activating the adapter. The Table extraction/projection described below now separates its native implementation while the default graph still retains the complete adapter. Other native features remain coupled, and no CLI installation or installed behavior is certified by this graph.

Native validation reads source as data and checks all discovered specs against iOS module/component providers, actual implementation classes (including multiple providers in `CUIFormMetadata.mm`), Android manager/module factories and module metadata, generated manager delegates and the custom owned focus descriptor. It checks the pod's source/public-header declarations, Gradle codegen/prefab wiring, both CMake targets, every owned C++ translation unit against the explicit motion source list, generated overlay source globs, the provider forwarding header/function and quoted owned includes. Native inventory includes Android manifest/consumer rules, Swift, C++ headers, licenses and upstream provenance; build/test outputs are excluded. Registration comments do not satisfy checks, and native config is parsed as a static object rather than imported or executed.

The prefab package `codon-ui_react-native` and link `codon-ui_react-native::codon_motion` are hardcoded by the current overlay build. Renaming a copied native package without coherently rewriting and verifying those references produces findings. The current package/codegen/Java/pod/target identities are deliberately a supported source profile, not configurable install destinations.

`valid` means the selected source graph and supported registration checks have no findings. It does not establish generated code correctness, native compilation/linkage, Metro resolution, autolinking, an installable registry item or installed-device behavior. The static native checks do not interpret arbitrary Ruby, Groovy or CMake. Dynamic native config and nonliteral JS imports are findings; unsupported platform variants, missing imports, undeclared packages, test imports, package escapes and symlinks also prevent validation. Invalid root/package manifests reject the call. The reader assumes a quiescent checkout; it is not a snapshot transaction against concurrent filesystem changes.

Later integration must choose component entrypoints, map source paths into editable consumer ownership, adapt the native package/build identities, preserve all codegen/provider/descriptors and shared sources, incorporate hashes/owners into the existing lock and update/diff/remove safety, and run actual generated-code/Metro/native consumer checks. The graph provides source evidence for that work and performs no writes or dependency installation. Mac project detection/routing work remains a separate integration boundary.

Run `pnpm -F @codon-ui/cli test:native-source`. These focused tests also run at the end of the existing CLI test command. They cover the maintained public barrel, selected component closures, shared ownership/hashes/notices, cycles, type-only specs, escaping/symlink paths, unresolved/platform/test imports, and mutated provider/package/descriptor/CMake/Gradle/prefab registrations. No SDK, emulator, simulator or publication step is invoked.

## Table extraction and selected native sources

The Table backend is extracted behind the existing shared `CUIMotionSnapshot.tableStickyPresentation` ABI. The ordinary full package continues to enable Table through its checked-in composition factories. No module/component provider, package, pod, codegen namespace, descriptor, prefab identity or JNI loader is added. No public TypeScript component or spec signature changes.

Table owns thirteen native inputs: `cpp/table/StickyConstraints.h`, `StickyPresentation.h/.cpp`, `StickyStyle.h/.cpp`; `ios/CUITableStickyPresentation.h/.mm` and `CUITableFeature.h/.mm`; `android/src/main/java/com/codonui/input/CUITableStickyPresentation.java` and `CUITableNativeSession.java`; and `android/src/main/jni/TableStickyJNI.h/.cpp`. The feature continues to reuse shared `PositionOwnership`, `FabricSnapshot`, `NativeStyle`, `PopStyle` and Fabric-manager access. These helpers stay in shared code once.

On iOS, `CUITableFeature.mm` owns the Table session, driver updates, retirement and synchronous request implementation. The shared motion module forwards the actual calling JSI runtime and retains argument/error conversion. Pop and Table keep one shared mutex and validity flag; invalidation retires pop before Table and preserves driver/service cleanup on the main queue. Presenter storage belongs to the Table feature. `CUINativeFeatures.h` is the private shared interface; `CUINativeFeatures.mm` composes the default full implementation.

On Android, `CUITableNativeSession` owns the Table handles, driver, latched failure, request guards and callback. It receives the original module monitor and validity flag, so request/mount/frame/retirement synchronization stays on the original monitor. The native driver now depends on that feature session. Shared `CUIMotionSnapshotModule` forwards the unchanged synchronous generated method and invokes feature cleanup in its existing UI-thread invalidation block. `TableStickyJNI.cpp` retains the original seven native function bodies and registers them on the private feature-session class. That class has an explicit consumer keep rule for native lookup/callbacks. `MotionSnapshotJNI.cpp` retains the sole `JNI_OnLoad` and calls one composition function from `NativeFeaturesJNI.cpp`.

`inspectTableNativeOwnership(reader, adapter, includeTable)` records every input's unit, registration claims, feature boundaries and cross-unit dependencies. Shared implementation no longer requires a concrete Table type outside the composition factories. Removing Table files without rewriting composition/build membership still returns `blocked`. The stable shared spec method is recorded as `shared-abi`, separately from feature implementation; its presence does not require duplicating the Table backend or providers.

`projectNativeTableSources(reader, adapter, includeTable)` is a non-writing source producer for later CLI integration. Full selection retains all 209 inventoried native/config/spec inputs, with no replacements. Core-only selection omits thirteen Table inputs and emits five replacements: iOS and Java unavailable-feature factories, the JNI registration aggregate, the CMake source list and consumer keep rules. Both keep ten specs and the same provider/descriptors. Full `codon_motion` owns nineteen translation units; core-only owns sixteen. Source and replacement hashes are returned separately so the later install/update/diff/remove path can track the emitted bytes and retain its existing protection for local edits. This helper does not authorize overwriting any edited consumer factory or build file.

Core-only keeps the ABI method and reports `Table sticky: feature not installed` if called. It contains no concrete Table includes, Java types, JNI registration or Table translation units. Composition rewrites require the supported full-source profile and exact single build/keep-rule lines; unknown files, changed factory wiring or unsupported source-list formatting are rejected. Applying a projection still belongs to the existing CLI ownership/lock lifecycle; Mac target routing and consumer fixture work remain separate.

The custom `react_codegen_CodonNativeOverlay` target continues to own the generated root `*.cpp` and `react/renderer/components/CodonNativeInputSpec/*.cpp` sources. React Native also emits a default `react_codegen_CodonNativeInputSpec` OBJECT target for those same inputs. Enabling both source-owning targets is invalid; `validateNativeCompileOwnership` rejects their overlapping translation units. Likewise, Table never claims a second copy of the shared providers/package/pod/prefab/loader, and repeated registration identities are rejected.

The focused tests retain frozen normalized statement hashes from source25206f24 for the moved Android request/mount/driver, Table JNI functions and iOS request/mount/cleanup, plus unchanged pop operations. Normalization removes trivia and adapts only the extracted context/session names, shared-mutex indirection and JSI string-conversion boundary. These are mechanical source-equivalence controls, not native execution. The tests also check delegation, lock/validity/cleanup ordering, Java native declarations versus seven registered JNI methods, the feature class keep rule and a single loader.

Materialized full and core-only temporary packages both pass the owned-source/configuration inspector. The pinned RN0.86.3 emitters produce byte-identical Android/iOS generated bindings and provider maps for them; the real generated CMake source identities have no competing owner, and the real `ReactCodegen.podspec` emitter retains all ten spec inputs. Podspec emission uses an empty `.xcodeproj` directory solely for path metadata. Neither native CMake configuration nor CocoaPods execution is performed. The projection and ownership plan keep `selectiveInstallValidated: false` until actual consumer build/link/runtime checks exist.

Checklist `NATIVE-CELL-03` and roadmap3.3.9–3.3.11/Table sticky criteria were read for this continuation. This pass verifies packaging/source extraction and code generation only; it adopts no Table G01 or installed-cell verdict. Both selected Android/iOS SDK compilation/linkage, matching affected consumers/products and real Table scroll/frame/ref/lease/interruption/cleanup behavior remain required. The cloud image lacks CMake/Ruby/Xcode and an admitted native SDK lane. No native guest, SDK patch, dependency upgrade, release or publication step is part of this pass.

Run `pnpm -F @codon-ui/cli test:native-source` for the source graph, ownership/code-generation and extraction/projection suites. Native compilation and installed qualification must use their separately admitted maintained workflows.

## Date-segment ownership and extraction boundary

`inspectDateSegmentOwnership` identifies one `CUIDateSegment` group shared by TimePicker, DateTimePicker and DateTimeRangePicker. The real source graphs give those three pickers runtime import ownership of the same spec; Button and Input have no date-spec runtime ownership while retaining shared type/build dependencies. One spec, iOS provider, Android manager and descriptor serve the group; registrations are not cloned per picker.

The assessment hashes twelve candidate inputs: the component spec; the C++ key-policy header; iOS segment, owned-field and date custom-content header/implementation pairs; and Android segment, manager, key-policy and owned-field classes. Removing them is currently unsafe. Shared keyboard scopes, ordinary-editor routing, focus observers, form metadata/focus/document membership and accessibility semantics use the concrete segment class or its owned-field helpers. The current source uses both kind-of and exact-class checks; replacing them with a broad protocol test could admit a different editor and change ownership/default/IME behavior.

Shared TypeScript ordinary-editor code also imports wire types from the component spec. Dropping that file from a retained source tree is different from dropping its codegen input. In addition, Gradle exports `cpp/input/DateSegmentKeyPolicy.h` through the `codon_motion` prefab header directory; no external usage is assumed, but removing that exposed header is a separate native contract decision. `validateDateSegmentOmission` reports retained native references, picker runtime requirements, shared type requirements and prefab-header exposure rather than emitting an unsafe projection. `projectionAvailable` and `selectiveInstallValidated` remain false.

A negative control coherently removes the date spec/provider/descriptor/manager factory from the supported source profile. The actual RN0.86.3 Android/iOS generators successfully emit nine bindings without the date descriptor, yet the remaining native source still has unresolved date includes and Java types. This proves why successful code generation alone cannot establish a removable editor boundary.

The safe current choice is to retain the date-segment group in the shared native baseline. A removable implementation needs an explicit decision about an owned-editor abstraction preserving exact identity admission, input/default/composition routing, form membership/focus and semantics; separation of shared wire types from selected codegen inputs; and the exposed prefab header policy. This pass does not make those consequential changes or alter any production native/date source. Table's implemented projection remains independent.

The normal Node-only source suite includes six date ownership/source/codegen cases. An additional opt-in host check compiles the actual C++ policy header with `g++` and the unchanged Java policy class with the available JDK compiler module, then compares all25keys×128modifier/composition/read-only/picker states (3,200 cases) plus explicit capture-priority controls. Run `pnpm -F @codon-ui/cli exec tsx src/helpers/nativeSource/dateSegmentPolicy.host.test.ts`; it is intentionally outside the normal CLI test command so no new host compiler requirement is imposed there. This is host algorithm execution, not Android/iOS SDK compilation, native editor routing or installed qualification. All native/date acceptance and SDK/consumer obligations remain unchanged.

## Native selection manifest and ownership lifecycle

`buildNativeSelection` produces an internal, deterministic native manifest and emitted byte payloads for explicitly supplied native clients. The caller resolves which components require native code and which require Table; the helper performs no routing or component-name inference. Repeated requests union their features. Every native client owns the shared unit, and Table clients also own the Table unit with its shared dependency. Date support remains in the shared baseline. No other feature extraction is enabled.

```ts
const selection = await buildNativeSelection({
  sourceRoot: "/checkout/packages/react-native",
  requests: [{ component: "input" }, { component: "table", features: ["table"] }],
})
const snapshot = await captureNativeConsumerSnapshot("/consumer/native/codon")
const plan = planNativeSelection({
  desired: selection.manifest,
  previous: null,
  snapshot,
  externalIdentities: [],
})
```

This example only builds a plan. Neither helper writes consumer files, state, package dependencies or configuration. An empty request set has no native artifacts; removing the final native client proposes cleanup subject to the same ownership/conflict checks. The current full/core projections still emit209/196 inputs and share the same ten codegen specs and native package/build identities.

The manifest has sorted requests, unit dependencies/owners, per-file source/emitted SHA-256 hashes and native registration/runtime identity claims. Its content ID and complete captured-source input ID use canonical JSON, without timestamps or absolute checkout paths. Source capture is re-inspected from memory before projection. Relocating identical source retains the same manifest ID; a source edit changes it. `validateNativeSelectionPayloads` checks the complete payload set against emitted hashes. Hashes provide content addressing and tamper/staleness detection, not authentication or install approval. Source capture still assumes a quiescent checkout, and the format remains internal rather than a new registry/lock contract.

Identity claims include the supported codegen/provider/descriptors/package/pod/CMake/prefab/JNI registrations, Java top-level classes (including package-private classes) and Objective-C implementation/explicit Swift `@objc` runtime names. Repeated scope/identity pairs are invalid, including duplicates attributed to the same unit. A caller supplies other installed native owners' identity claims; any overlap blocks a plan. This helper does not discover other autolinked packages or comprehensively infer C++ symbols, generated/inner classes, preprocessor outcomes, Objective-C categories or arbitrary native build languages. Categories require an explicit profile rather than being silently accepted. Compiler/linker and whole-consumer registration checks remain required.

`defineNativeSelectionState` records the prior manifest and managed path subset at one normalized absolute consumer root. Omitting a path models previously released ownership, without adding public ejection behavior. The planner keeps shared files once as owners enter/leave. Removing one of several Table owners changes ownership metadata only; removing the last proposes thirteen deletions and five composition replacements. Dates remain while any shared client remains. The internal state must eventually map into the existing CLI installed-hash/ownership-state lifecycle; it is not an alternate lockfile writer.

| Observed ownership/content                                    | Planned behavior                                                                                            |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Incoming bytes unchanged                                      | Preserve consumer edits or deletions; retain the original baseline hash.                                    |
| Incoming bytes changed; current bytes match recorded baseline | Propose replacement with before/after hashes.                                                               |
| Current bytes already match incoming bytes                    | Keep them and advance the expected baseline.                                                                |
| Incoming change affects an edited/deleted owned input         | Block the complete transition.                                                                              |
| Retired owned input matches baseline or is absent             | Propose deletion or release the missing input.                                                              |
| Retired owned input was edited                                | Block the complete transition.                                                                              |
| New target already exists, even with matching bytes           | Block; byte equality does not grant ownership.                                                              |
| Previously released input                                     | Preserve without readoption; block required updates or retained native source that would lose dependencies. |

Every conflict returns zero operations and no next state. A ready plan contains proposed operations and a proposed next state, which a future writer may persist only after successful checked application. The planner never blesses local edits as a new baseline. Unknown source/configuration in this native build domain blocks planning because pod/Java globs or registration may include it; inert Markdown/text/license metadata is retained. Structural file/directory migrations, links and case/path collisions fail closed. Adoption, force/merge policy, destination rewriting and other consumer migration decisions remain integration work.

`captureNativeConsumerSnapshot` hashes source-domain files and records directory/link/other entries without traversing observed symlinks. It ignores only the listed generated trees in `NATIVE_SNAPSHOT_IGNORED_TREES`: root `.git`, `node_modules`, `build`, `dist`, Android `.gradle`/`.cxx`/`build` and iOS `Pods`. Inputs overlapping ignored trees are rejected. Portable relative paths reject escapes, reserved Windows names, case collisions and file/directory ambiguity. Root or ancestor links are rejected. The snapshot, prior state, desired manifest and sorted external claims bind the plan ID to this consumer root. `validateNativeSelectionPlan` recomputes it against fresh inputs to reject stale plans, including unknown added/deleted files. This is a read-only observation and revalidation protocol, not a filesystem transaction: a later writer must prevent or detect changes between its final check and mutation, handle rollback and commit ownership only with successfully applied bytes.

Eighteen additional Node-only cases cover deterministic requests/IDs, complete payloads/materialized real native source inspection, relocated/edited source identities, shared/feature ownership transitions, local edit/deletion retention and conflicts, released ownership, duplicate native identities, unknown-source orphan protection, path/link conflicts and stale-plan rejection. They run in `test:native-source` and the normal CLI suite. They invoke no SDK and establish no autolinking, native compilation/linkage, installed behavior or selective-install qualification. `selectiveInstallValidated` remains false; Mac routing, existing CLI commands/lockfiles and the consumer fixture lane are untouched.

## Transaction execution and filesystem integration boundary

The existing strict writers do not expose a reusable transaction/rollback primitive. `writeStrictRegistryInstall` in `installPlan/strictAdd.ts` writes transformed files then the existing consumer lockfile; `writeStrictUpdate` in `updateStrict.ts` and `writeStrictRemove` in `removeStrict.ts` likewise mutate files before writing the lockfile. This observation does not change their behavior or qualify them for native transaction application. A separate native filesystem writer would leave two write paths to reconcile and would not make the combined source/lock update atomic.

`executeNativeSelectionTransaction` is a decoupled execution/compensation kernel for the native lifecycle plan, with an explicit `TNativeTransactionStore` capability contract. It supplies no filesystem adapter, new CLI writer, lockfile format, dependency installer or durable recovery journal. The only store implementation in this pass is an executable versioned model inside its tests. Do not connect an ordinary `readFile`/`writeFile`/`rename` wrapper and treat the contract as satisfied.

Before any mutation, the kernel clones the manifest, plan and payload bytes, validates their content IDs and complete payload hashes, obtains a fresh guarded source view and metadata context, reads and verifies every required before-image, then rechecks the view/context. Root and missing parent directory creation are explicit ordered mutations. Existing empty directories are retained during ordinary removal. Each exchange must atomically compare the root, every ancestor and target identity/kind/hash, reject links or case aliases, create missing targets exclusively and remove directories only when empty. A rejected exchange must guarantee no effect; thrown, malformed or explicitly uncertain outcomes require recovery rather than being assumed to have failed before writing.

The guarded view contains opaque version evidence for both present entries and every requested absent path. A content hash alone is insufficient: same-byte writes must change the file version, and a consumer creating and then deleting an absent path must change that absence version. Otherwise rollback could restore a retired file over a consumer's later deletion. Directory identity tokens stay stable while children change, but root/directory replacement must invalidate guards. Tokens cannot be reused or aliased within the transaction. These are requirements for a future adapter, not guarantees provided by `captureNativeConsumerSnapshot` or ordinary filesystem timestamps.

Acknowledged effects are journaled in memory and compensated in reverse order after failure. Compensation uses the exact post-operation version/ancestor guards, so consumer edits, recreated files and replaced roots/parents are preserved. A consumer file inside a newly created directory prevents its cleanup; recursive removal is not used. A blocked compensation does not stop other safe compensation. Recovery entries retain original byte images, attempted post-image hashes/kinds, guards, affected paths and failure phases for review. An uncertain step is never blindly undone. `rolled-back` means all acknowledged transaction effects were compensated; unrelated consumer changes may remain. `recovery-required` retains unresolved or ambiguous effects. Neither failure status returns a proposed next state.

Completion rechecks the entire source view and current ownership/external-identity context before returning `applied` with a proposed next state. The kernel never persists that state. Mutation counts include root/directory operations as well as file operations. The journal is volatile and before-images currently describe bytes/kinds only: this is not process/power-loss recovery, a metadata/mode/xattr preservation implementation or proof against arbitrary concurrent filesystem writers. No consumer filesystem application is exercised by these model tests.

The remaining consequential decision is how the real consumer writer controls concurrent editors and provides guarded mutations, identity/absence versions and durable recovery. Path checks followed by separate Node writes do not provide atomic compare-and-exchange against root/ancestor swaps, in-place edits or create/delete races. A cooperative/exclusive editing boundary or a separately verified platform storage strategy is needed; this pass does not silently choose one or weaken the adapter contract. Native SDK/build/installed proof also remains required, and `selectiveInstallValidated` stays false.

The actual integration path is to prepare transformed ordinary/native bytes and the existing next lockfile data before applying anything, then route them through one reviewed shared transaction boundary. Reuse the current CLI lock schema and ownership decisions. Do not apply this native transaction and then call an unchanged direct writer to commit the remaining files/lockfile. Package-manager effects need their own explicit treatment and are outside this byte transaction. Mac target routing and consumer fixture work remain independent; no existing command imports this kernel.

Eighteen Node-only transaction cases exercise actual full/core native payloads against the store model, every one of the eighteen Table mutation failure boundaries, initial directory creation/rollback, stale views/context, payload tampering/traversal, corrupt before-images, root/ancestor changes, same-byte edits, presence/absence ABA changes, consumer recreation, partial/failed rollback, unknown outcomes and invalid receipts. They run in `test:native-source` and the normal CLI suite alongside the existing source/code-generation tests. This evidence establishes execution/compensation behavior under the stated adapter contract, not a filesystem implementation or native consumer installation.
