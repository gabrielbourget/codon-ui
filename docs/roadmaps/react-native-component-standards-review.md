## Scope And Outcome

Reviewed the fourteen current native counterparts, their public types, shared theme/content/color/interaction utilities and overlay support against the corresponding React component patterns and [AGENTS.md](../../AGENTS.md). The twelve earlier controls are the primary prerequisite review; the three trial targets and their infrastructure were also screened for integration boundaries. The inventory contains 54 runtime TypeScript/TSX files. The review covers code organization, state ownership, prop/ref/event boundaries, style precedence, shared-helper ownership, platform branches and focused-test coverage. It is a source-quality review, not a replacement for installed or physical acceptance.

The source meets the existing shared formatting/lint/type/public-contract gates. All 309 native cases across 17 suites pass in 9.506 seconds. No confirmed behavioral defect requiring a source correction was found in this pass. Organizational differences remain: substantial calibration is inline in several components, a content helper named for Button serves other controls, private style recipes repeat and some style literals use assertions where new code could use explicit types. These are maintainability observations to address at natural edit boundaries rather than a reason to invalidate the accepted archive with a broad refactor before the trial.

The React package generally uses a thin component, calibration helpers and CSS modules; the native package shares the design vocabulary and presets but cannot reproduce a browser cascade or CSS inheritance directly. NativeThemeProvider and NativeContentContext explicitly carry those roles. Native rendering/context/state ownership deserves its own clear conventions while keeping the React code recognizable.

## Existing Requirements To Keep

- Use the shared ESLint, Prettier and TypeScript presets; double quotes, no unnecessary semicolons, arrow functions, descriptive names, T-prefixed internal types and constants-derived unions. Compatibility export aliases can retain their established names.
- Keep controlled values authoritative. Treat false, zero, empty string/array and contract-defined null distinctly from undefined. Preserve the established controlled/default and callback semantics; no effect-driven mirror may silently replace ownership.
- Keep native props/ref/event types honest. Spread general props before owned semantics/handlers/styles; compose allowed callbacks once; keep disabled/read-only/pending and cancellation guards at the actual activation boundary.
- Preserve typed semantic theme roles, the current hand-authored palette and native style precedence. Prefer owned context for text foreground rather than cloning unknown child components. Do not assume that CSS variables, DOM classes or browser inheritance exist in native views.
- Use shared TypeScript/TSX and ordinary React Native primitives by default. Localized platform choices for target minima, keyboard behavior, numeric keyboard and native completion are justified by existing contracts; separate platform files or custom native modules need a demonstrated reason.
- Verify changed behavior at the narrowest useful tier, preserve source/binary identity and distinguish source tests from installed/physical accessibility and touch acceptance.

## Candidate Native Styling Standards

**Candidate A — Typed calibration helpers, recommended for substantial styling.** Keep the component focused on state/hooks, native props and rendering. Put nontrivial theme/prop/state-to-style calculations in a colocated styles.ts or helpers.ts, returning named style slots and any resolved foreground needed by owned text. Keep model/collection logic separate. A helper should be a pure function receiving theme/props/state, rather than a second component or hidden hook. Use the existing descriptive getNative…Style naming consistently within a touched component; do not rename the entire package merely to match the web calibrateComponent spelling. This is the closest practical analogue of web helpers plus CSS modules.

**Candidate B — Static StyleSheet.create for genuinely static structure, compatible with A.** Module-level StyleSheet entries can name repeated structural layout without adding a styling runtime. Theme/state/prop-derived values still belong in typed calibration. Small local layout objects are acceptable when they make the JSX easier to read; do not extract every flex row or memoize every object automatically. Performance-driven caching should follow measurement and preserve theme updates.

**Candidate C — Utility classes or another styling runtime, deferred.** NativeWind/Uniwind or a styled-components-style system could be evaluated separately, but would change dependency/tooling conventions and does not itself solve native state, context, focus or layout ownership. The RN Primitives trial does not need such a system. Preserve Codon's current styling while evaluating headless behavior.

Recommend A with selective B for new trial code and future substantive component edits. Keep hook/event code out of style helpers; keep minimal structural styles inline where clearer. Prefer explicitly typed literals or satisfies over assertions in new code, while recognizing that current assertions are not a demonstrated runtime defect. Keep style slots and computed → customStyles → final style precedence explicit. Tests should verify public style/state behavior, not private filenames or exact object-construction syntax.

## Follow-Ups And Review Boundaries

1. During a future touched-component pass, extract substantial Switch/Checkbox/Radio/Input/TextArea/NumberInput/AlertDialog calibration without changing values or ownership. Keep each extraction coherent and prove public behavior; do not combine it with a dependency migration by default.
2. When the common phrase-content helper is next changed, move or rename it to reflect its actual private shared ownership, then update consumers together. Avoid a new public utility/API or another cross-package abstraction.
3. Repeated shadow/focus recipes may become private helpers if a concrete edit benefits. Promoting them into public theme fields would be a separate contract decision; do not alter the palette or theme shape in a code-organization pass.
4. Preserve intentional API differences, including earlier Input/Checkbox optional naming versus later explicitly named components and NumberInput's bounded formatting options. Any normalization that narrows public props requires a concrete contract proposal, not a style cleanup.

The owner can iterate these candidates in this document. No lint rule, filename mandate, public API restriction, styling dependency or wholesale refactor is enacted by recording them. The [approved RN Primitives trial](react-native-primitives-adoption-proposal.md) follows this prerequisite review and will use thin rendering with typed calibration in its shared TypeScript fixtures. Production adoption remains gated by its own host/context/state results.
